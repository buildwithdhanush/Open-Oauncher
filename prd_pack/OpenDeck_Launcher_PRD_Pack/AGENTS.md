# Agent instructions — OpenDeck Launcher

You are implementing an original Android launcher from `PRD.md`. Treat the PRD as the product contract.

## Non-negotiable rules

1. Build an independent product. Do not copy Total Launcher source code, DEX methods, assets, fonts, serialized layout files, proprietary text, screenshots, branding, package name, or UI artwork.
2. Do not patch, bypass, emulate, or interfere with Total Launcher billing, licensing, signatures, or premium entitlement checks. OpenDeck has no billing or feature locks; implement its own requested capabilities.
3. Do not claim static analysis proves unobserved behaviour. Follow the evidence levels in `REVERSE_ENGINEERING_EVIDENCE.md` and the gap disposition in `GAP_AUDIT.md`.
4. Use Kotlin and the Android SDK. No Python/Node runtime inside the APK, no root, no shell command execution, no hidden APIs, no remote code loading.
5. Core launcher functionality must work offline and with optional permissions denied.
6. Request sensitive permissions only when a user enables the corresponding feature. Do not request contacts, calendar, location, notification access, or broad storage permission on first launch.
7. Do not use AccessibilityService or DeviceAdmin for normal launcher actions. Do not scrape other apps' screens or notifications.
8. Use official Android APIs for Home role, app widgets, shortcuts, wallpapers, system settings, and document selection.
9. Keep every exported component protected and validated. No arbitrary external Intent or action sequence may execute.
10. No feature can be marked done without implementation, automated tests, and a manual verification note where device behaviour is involved.

## Execution protocol

For each task:

1. State the requirement IDs being implemented.
2. Inspect the current repository before editing. Do not replace existing architecture blindly.
3. Propose the smallest implementation plan and identify files to change.
4. Implement in a small, buildable diff.
5. Run relevant unit tests, Android Lint, and build tasks.
6. Inspect the final diff for permission, privacy, lifecycle, and backup effects.
7. Report `Implemented`, `Partial`, `Missing`, `Incorrect`, and `Needs Verification` separately.
8. Do not mark a feature complete if it only has UI placeholders or mocked data.

## Coding conventions

- Kotlin, coroutines, Room/SQLite, DataStore, AndroidX where useful.
- Views/custom ViewGroup for the workspace; do not place a heavy Compose renderer around AppWidgetHostView.
- Keep files under 500 lines where practical; split focused classes.
- Use interfaces around PackageManager, AppWidgetManager, WallpaperManager, SAF, and optional integrations.
- Persist normalized geometry, stable IDs, and explicit schema versions.
- Use database transactions for multi-entity edits and restore.
- Validate imported backups/themes as untrusted input; no path traversal, executable content, or arbitrary object deserialization.
- Never store credentials or secrets in source control.

## First tasks

1. Read `PRD.md` and `REVERSE_ENGINEERING_EVIDENCE.md` completely.
2. Create `ARCHITECTURE.md`, `DATA_MODEL.md`, `PERMISSIONS.md`, `BACKUP_FORMAT.md`, and `TEST_PLAN.md` from the PRD before complex implementation.
3. Create a buildable Android project and CI with an empty Home activity.
4. Implement app discovery and drawer, then workspace pages and edit mode.
5. Add widgets, folders, panels, items, themes, actions, backup, and optional integrations in the order specified in PRD milestones.

## Build acceptance

At every milestone, the project must build. Never generate a fake APK or call a placeholder screen a completed launcher. Provide the exact Gradle commands run and their results. The release APK must be generated by the build pipeline and signed with a project-owned release key kept outside the repository.


## Feature-completeness rule

A requirement marked P2 is still part of the requested final product. P2 means user-enabled/optional at runtime. Do not omit it from the final implementation or call the app feature-complete while it is missing. Early builds must publish a gap list.
